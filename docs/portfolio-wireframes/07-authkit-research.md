# AuthKit visual-explanation research

## Scope

Research completed against the live [AuthKit website](https://www.authkit.com/)
and the three supplied reference screenshots on 2026-08-15. This is a study of
its communication pattern, not a request to reproduce its artwork, interface,
copy, or brand identity.

## What the live page does

AuthKit repeatedly pairs a product claim with a dedicated visual proof module:

1. **Authentication examples** show the same basic sign-in task in several
   realistic interface states: password, social sign-in, and one-time code.
2. **Extensibility** places the customization claim beside a dashboard-style
   visual, making user updates and realtime APIs feel concrete rather than
   abstract.
3. **Customization** shows a working login screen beside controls for colour,
   logo, radius, appearance, and button/link colors.
4. **Security** turns five individual capabilities into labelled mini-scenes
   instead of a bullet list: leaked-password protection, role-based access,
   password strength, bot detection, and multi-factor authentication.
5. **Enterprise readiness** uses one large, labelled system composition to
   show how email/password, social login, MFA, SSO, and directory sync connect
   to a broader platform.

## What the supplied screenshots make especially clear

### Screenshot 01 — capability cards

Each card contains an intentionally simplified object or signal. The title is
the claim; the illustration is the mental model. The viewer does not need to
read a paragraph to understand that the feature concerns a password, role
controls, password validation, bot detection, or MFA.

### Screenshot 02 — labelled integration surface

One large central visual is surrounded by capability labels. This creates a
clear hierarchy: an entry method leads into a shared system, which unlocks
several connected enterprise outcomes.

### Screenshot 03 — compositional system canvas

Code, UI components, design tokens, verification, and status feedback coexist
on one visual plane. The image communicates that a real capability is produced
by several coordinated layers.

## Pattern to borrow for the portfolio

Use a **visual proof module** for each significant engineering decision:

- a plain-language title;
- a diagram with named product/system stages;
- a short interpretation of the decision;
- a verified outcome or a clearly labelled qualitative result.

The diagram must describe the project itself, for example a protocol route,
grounded AI context pipeline, or tenant trust boundary. It must not be a
generic decorative network.

## Explicit boundaries

- Do not copy AuthKit’s dark navy, glow-heavy, device-like 3D rendering.
- Do not borrow its asset shapes, screen designs, words, or product features.
- Do not turn every project section into a card grid.
- Keep the portfolio's existing editorial, light, work-first direction.
